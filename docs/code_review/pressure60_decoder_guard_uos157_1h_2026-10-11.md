# uos157：解码帧身份防护后的 60 路分析 × 4 FPS × 1 小时复测

日期和展示时间：2026-10-11，Asia/Seoul（KST，UTC+09:00）。

**防崩溃结果：通过本轮观测；总体业务验收未通过。** 本轮 Savant A/B 的累计重启数为 0/0，正式期内指标窗口拦截重复或异常解码输出 80 个；2,825/2,825 条应取证视频保存，超过 180 秒 0 条，最长 114.639 秒。抽样完整解码 0/12 通过，2,753 条居中未验证，不能据此宣称“所有完整视频三分钟内保存”已验收。

## 一个必须更正的负载条件

本轮模型分析确实是 60 路（A/B 各 30），但在 2026-10-11T05:06:56.595317+09:00 的全量 Docker 盘点中，**源适配器实际运行 100 个：本轮 60 个 + 旧测试 40 个**。推流机同期确认到 uos157 的 RTSP TCP 连接 100 个。旧容器继续读取同一个电影地址，增加分发、网络和宿主机开销。因此本轮只能说明带背景输入负载时的稳定性与生成事件登记时效，不能作为隔离的纯 60 路容量认证。

原 runner 的 `prepare_evidence_guard()` 在 `force_runtime_restart` 时提前返回，跳过了停用旧源。之前准备及监控仅按 run ID 核对 60 个目标源，没有核对全部 reader，是本次测试设置和检查中的遗漏。当前正式时段没有中途停止旧源，以保留整小时同一工况；缺陷与证据一并留档。

本地后续修复使强制重启仍先 quiesce 旧源，并在正式采样前核对 Docker 中全部动态/compose 源：必须恰好等于目标源集合，额外或缺失源都会阻止开始。新增回归在原版复现“未停用旧源”，修复后通过。该 runner 修复与共享输入脚本在一小时开始后编写，**不属于本轮被测 b865999 归档**。

## 自动重启的原因与防护效果

原故障是解码输出携带了已经通过 source-convert、甚至已经进入 muxer 的帧索引，原生 C probe 再次将它移向 source-convert，Rust 阶段顺序检查 panic 并终止进程，Docker `unless-stopped` 重启容器。不是服务器重启，已捕获状态不支持 OOM 解释。

补丁将 source-convert 的原生移动 probe 替换为 Python `VideoPipeline.move_as_is` 路径。真实绑定遇到非法回退时抛出可捕获 ValueError；每个输出 pad 的有界 ID 历史还拦截尚未离开同一阶段的重复输出。校验 source/metadata，拒绝已删除或已入 batch 的对象；允许唯一 ID 的正常重排；不重写 UUID/PTS，不删除原在途对象。按原因累计计数并限频记录诊断。

## 输入损坏已有独立证据

压测负载期间，在 uos157 直接用 FFmpeg 读取 RTSP（绕过 Savant/forwarder/media-worker）也解码失败；录制后跳过前 5 秒再解码仍失败。两份并行 adapter 捕获分别使用 wallclock PTS 和原生 PTS，均失败，不能单靠关掉 wallclock 就宣称输入已修好。推流机 loopback 同时段 20 秒解码通过。

MediaMTX 明确记录 `reader is too slow, discarding ... frames`。三个警告 session 的读路径已追到 `live/1080movie`，都是 TCP。syslog 使用 Asia/Shanghai，示例原始 `03:46:30` 对应首尔 `04:46:30`；保留原文。摘录尾部共有 29,196 条警告，但这是有界日志，不是正式一小时总计；不将 MediaMTX 的日志单位直接等同于丢失视频帧。

推流机到 uos157 经 wlan0，现场一次发出流量采样约 138.6 Mbps。结合 100 个 reader 与服务器丢弃日志，输入分发拥堵已确认；无线瞬时停顿、服务端队列和下游背压各占多少尚未分离，不把无线标称速率当成吞吐上限。

## 修复后的输入验证与恢复

正式测试结束并恢复后，临时停用 40 个旧 reader，分别进行 90 秒 60 客户端直拉与本机共享输入短测。直拉完整解码通过 4/4；共享输入通过 4/4。原 40 个容器身份及运行状态已恢复。此检查没有模型推理和证据写入，不能代替新的完整业务一小时验收。

新增 `run_shared_rtsp_relay.py` 使用既有 Savant 镜像内的 GstRtspServer，共享一个上游 H264 RTSP 会话给本机多个 TCP 客户端，不解码、不编码、不做抽帧。60 个 source adapter 仍可分别赋予独立 source ID。原生自包含检查已验证两个解码客户端共用一个上游 session。

本轮正式测试最终恢复核验时间 **2026-10-11T06:14:44.684389+09:00**：日常原有容器配置与启停状态已核验，PostgreSQL/Redis 身份保留，摄像头/性能/拓扑/生成配置恢复，测试源停止，推理服务恢复原停止状态，GPU 计算进程为 0。测试证据与原历史证据均保留。恢复的 40 个旧 reader 是测试前状态；其额外输入开销已明确记录，后续正式验收必须隔离。

修复相关 23 项测试通过，真实 Gst/Rust 调用验证非法回退不会终止进程。后续隔离相关 6 项、遥测兼容相关 4 项通过；guard、loader 与压力 runner 整体用例共 243 通过、5 失败，这 5 项在未修改的 b865999 基线也失败（本地 Docker 缺失或既有 300/600 秒 fixture 不匹配）。原 deployment contract 的 4 项失败也已与未修改基线核对，不写成全量测试全绿。
