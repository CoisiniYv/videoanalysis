## 按用户明确的 180 秒保存要求补充判定

用户随后明确，首要要求是所有应生成的视频证据在 3 分钟内保存好。
因此业务时限以告警对应帧的事件时间开始，包含分析排队、事件入库、取证后置
等待、视频生成与数据库发布；要求逐条 <=180 秒，不能只检查 p95。

2026-10-10 对本轮已有数据库记录做只读补查，没有重跑负载或修改运行配置：

| 正式采样期 526 个入侵视频 | 最长耗时 | 超过 180 秒 |
|---|---:|---:|
| 事件帧时间 → worker 记录的处理完成 | 95.200 秒 | 0 |
| 事件帧时间 → 取证任务最后更新 | 95.719 秒 | 0 |
| 事件帧时间 → 证据 bundle 最后更新 | 95.639 秒 | 0 |
| 事件入库 → worker 记录的处理完成 | 59.931 秒 | 0 |

526 条视频覆盖全部 60 路，完成时间字段无缺失。含预热和收尾的全部 586 条
视频，事件入库至完成也全部低于 180 秒。

**本轮短测的视频保存时限通过；脚本的严格压力门槛未通过；25 条视频的事件
居中质量校验待定位。** 这是三个分别判断的结论。3.9137 FPS 和非零分析队列
是持续容量健康指标，不能单独据此宣称违反了 180 秒保存要求；同样，任务
完成不能替代证据内容与锚定的质量验证。短测全量满足时限不等同于已证明
长时间持续运行时每条都满足时限。

后续验收应同时报告应取证数、完整可播放视频数、180 秒内完成数、最慢耗时、
未完成/失败/超时数，以及未通过质量校验数。FIFO 过期丢帧与 UUID 优先修改
仍是待证据支持的方案；用户此项澄清不表示已授权通过丢弃应取证事件来提高
完成比例，也不构成自动取消事件居中校验的依据。

吞吐以帧计数差为准。短窗口在追赶积压时会超过 4 FPS，直接平均这些 gauge
会掩盖整段吞吐不足。队列也会增长和回落，不能把短测解释为无限增长，
但这轮并未维持无积压运行。

脚本记录四项失败：

```text
steady_effective_fps_below_minimum
forwarder_queue_full
forwarder_queue_nonzero
validate_seq_iq_exceeded
```

`forwarder_queue_full` 来自脚本对聚合队列 >= 2,048 的判定，本轮有 13 次采样
满足该条件；它不能单独证明各分支的实际队列都装满或已丢帧。
Savant 日志中有 178,422 条 `validate_seq_iq` 警告。主动从约 24 FPS 重采样到
4 FPS 也会造成 seq_id 跳跃，不能把这个数字等同于真实丢帧数量。
main 脚本在本轮同时存在队列问题时将它列入失败原因。
另有 `tensorrt_engine_mps_partition_warning`，脚本保留为 MPS 分区警告。
